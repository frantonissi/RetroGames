ESPECIFICAÇÃO TÉCNICA

RetroGames — Arquitetura e Stack
Versão 1.0 · Escopo: Módulo de Catálogo e Administração




1. Visão geral

1.1 Objetivo
Este documento especifica a arquitetura, a stack tecnológica, o modelo de dados, os contratos da API e os
requisitos de segurança do sistema RetroGames, uma loja web de jogos retrô usados. O escopo desta versão
é o Módulo de Catálogo e Administração.

1.2 Funcionalidades
A tabela a seguir delimita as funcionalidades contempladas nesta versão.

 Funcionalidade
 Catálogo público de jogos, com busca textual, filtros por plataforma e gênero e paginação
 Consulta de detalhe de jogo
 Manutenção de plataformas (inclusão, consulta, alteração e exclusão)
 Manutenção de jogos, com associação a gêneros (relação N:N) e exclusão lógica
 Consulta de gêneros e de condições de jogo (tabelas de domínio)
 Autenticação e autorização do perfil Administrador



1.3 Visão de componentes
O sistema é composto por três componentes executados localmente: uma Single Page Application (SPA) em
React, uma API REST em ASP.NET Core e um banco de dados relacional MySQL. A SPA comunica-se
exclusivamente com a API por HTTP/JSON. A API acessa o banco de dados por meio do ADO.NET, com o
provedor MySqlConnector.
Em ambiente de desenvolvimento, o servidor do Vite (porta 5173) encaminha as requisições com prefixo
/api para a API (porta 5080). Front-end e API compartilham a mesma origem, o que dispensa a configuração
de CORS e permite o uso de cookies SameSite=Strict.

3. Arquitetura

3.1 Estilo arquitetural
O back-end adota arquitetura em camadas. Cada camada depende apenas da camada imediatamente
inferior:
Controller → Service → Repository → banco de dados.
É vedado ao controller acessar o repositório diretamente. Somente a camada Repository contém instruções
SQL. A camada Service não depende de tipos HTTP (HttpContext, códigos de status). O controle de
transações é responsabilidade exclusiva da camada Service. Há um Repository por tabela, com o nome dela
sem o prefixo tb_ (tb_condicao_jogo → CondicaoJogoRepository); cada um retorna entidades de uma única
tabela, sem junções nem subconsultas em outras tabelas; filtros, ordenação e paginação são aplicados no
SQL. A composição de dados de várias tabelas é feita no Service, com LINQ, e resulta em um ServiceModel.
Filtros que dependem de outra tabela, como o filtro por gênero, também são resolvidos no Service: a seleção
é feita com LINQ e o resultado segue para o SQL como lista de identificadores, o que mantém a contagem e a
paginação no banco.

3.4 Fluxo de processamento de uma requisição
Exemplo: inclusão de plataforma (POST /api/Plataforma).
    1.​ Na tela de plataformas, o formulário chama plataformaApi.inserir, em servicos.js, que
        envia POST /api/Plataforma pelo Axios.
    2.​ A requisição chega com corpo JSON e com o cookie de sessão, que o navegador envia sozinho.
    3.​ O ASP.NET Core confere a sessão e o perfil Administrador. Em seguida, o FluentValidation valida o
        InserirPlataformaApiModel; em caso de erro, a API responde HTTP 400 com responseCode 3.
    4.​ O PlataformaController converte o ApiModel na entidade Plataforma e invoca
        IPlataformaService.InserirAsync.
    5.​ O PlataformaService verifica a unicidade do nome.
            a.​ Em caso de duplicidade, lança BusinessRuleException, convertida em HTTP 409
                 (responseCode 101).
    6.​ O IPlataformaRepository.InserirAsync executa INSERT parametrizado e retorna o
        identificador gerado (LastInsertedId).
    7.​ Se outra requisição gravar o mesmo nome entre a verificação e o INSERT, o banco recusa a gravação
        (erro 1062); o Repository lança RegistroDuplicadoException e o Service a converte no mesmo
        erro de negócio (HTTP 409, responseCode 101).
    8.​ O controller responde HTTP 201 com o recurso criado no envelope.
    9.​ No front-end, plataformaApi.inserir devolve o conteúdo de data; em caso de erro, a tela
        exibe errorMessage.

4.3 Restrições de integridade
   ●​ O banco de dados é responsável exclusivamente pela integridade estrutural: chaves primárias, chaves
      estrangeiras, tipos de dados e obrigatoriedade (NOT NULL) e unicidade (UNIQUE).
   ●​ É vedado o uso de triggers, functions e ações referenciais (ON DELETE CASCADE, ON DELETE SET
      NULL). As chaves estrangeiras mantêm o comportamento padrão do MySQL.
   ●​ Toda regra de negócio (unicidade, faixas de valores, exclusão lógica e manutenção de registros
      dependentes) é implementada na camada Service. Quando uma operação exige mais de um
      comando, como a gravação de um jogo e de suas associações em tb_jogo_genero, o Service abre
      a transação com TransactionScope e a conclui com Complete(). O Repository apenas executa
      os comandos SQL e é vedado a ele abrir, confirmar ou desfazer transações. A unicidade é conferida
      pelo Service e garantida também pelo UNIQUE do banco: se duas gravações simultâneas passarem
      pela conferência, o banco recusa a segunda (erro 1062), o Repository lança
      RegistroDuplicadoException e o Service a converte no erro de negócio correspondente.

5.3 Envelope de resposta
Todas as respostas, de sucesso ou de erro, utilizam o envelope abaixo. Em falhas de validação (responseCode
3), data contém os erros indexados por campo. Os códigos são declarados em dois catálogos, sem repetição:
ResponseCodes (projeto ApiModels), de 0 a 99, no formato (Code, DefaultMessage), com os códigos que
nascem na própria API; e BusinessErrors (projeto Services), a partir de 100, no formato (Code,
DefaultMessage, Status), com os erros de negócio e o status HTTP de cada um, indicado na tabela ao lado do
código. O envelope devolve o código do erro de negócio lançado pelo Service. Em cada catálogo, um novo
código recebe o próximo número livre. Os códigos do Módulo de Compras serão definidos na tarefa
correspondente. A propriedade data é omitida nas respostas de erro, exceto na falha de validação. A seção
5.4 apresenta exemplos.

9. Testes

  ●​ Tipo: testes unitários com xUnit v3 e Moq. Testes de integração não fazem parte do escopo.
  ●​ Alvos: controllers, com o service substituído por mock; services, com o repositório substituído por
     mock; GlobalExceptionHandler. Também são testados os validators, com casos válidos e
     inválidos. A seção 7.1 relaciona os testes às funcionalidades e às regras.
  ●​ Padrão: Arrange, Act, Assert (AAA), com um único comportamento verificado por teste.
  ●​ Execução: dotnet test na raiz da solução. Todos os testes devem passar antes de cada commit na
     branch principal.
10. Execução local

Pré-requisitos: .NET SDK 10, Node.js 22 LTS e MySQL 8 em execução.
    1.​ Criar o banco de dados e deixar executando.
    2.​ Copiar .env.example para .env, na raiz do repositório, e preencher ConnectionStrings__Default,
        AdminInicial__Email e AdminInicial__Senha.
    3.​ Executar dotnet run no projeto RetroGames.WebApi. A API responde na porta 5080 e o Swagger
        UI fica disponível em /swagger.
    4.​ Executar npm install.
    5.​ Execute npm run dev no diretório retrogames.web. A aplicação responde na porta 5173.
    6.​ Executar dotnet test na raiz da solução para validar os testes unitários.
